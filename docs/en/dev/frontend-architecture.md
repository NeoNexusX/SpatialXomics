## Directory Responsibilities

- `src/app`: application shell and global entry components.
- `src/views`: route pages that compose feature capabilities; existing pages may contain limited page-coordination logic.
- `src/shared`: HTTP, authentication, configuration, directives (`v-reveal`), generic components, composables, types, and utilities that do not belong to one business feature.
- `src/features/<module>`: business modules with `api`, `components`, `composables`, `constants`, `mappers`, `services`, `stores`, `types`, or `utils` as needed. Current modules: `agent`, `auth`, `collections`, `databases`, `datasets`, `home`, `upload`, `users`, `vizworkbench`, `workspace`.
- `src/i18n`: the app-wide vue-i18n instance, type definitions, and locale messages. Messages are organized as `locales/{locale}/{namespace}.json`; core namespaces (`common`, `auth`) are loaded at startup, while feature namespaces are lazy-loaded alongside their routes.
- `src/services`: infrastructure-oriented readers and clients shared by multiple features — Zarr (`zarr`, including its OSS client), clustering, and PubChem.
- `src/router`: route declarations plus authentication/authorization guards.
- `src/workers`: the worker shared by the upload flow; feature-owned workers may remain inside their module.

## Dependency Direction

- `shared` should not depend on a concrete `features` module.
- Features may depend on `shared` and cross-module `services`.
- Avoid reaching directly into another feature's internals. Extract genuinely shared behavior to an appropriate `shared` or `services` API.
- Views and workspace pages may compose multiple features, while requests, calculations, and side effects should normally live in composables/services.
- **Locale message files must live under `src/i18n/locales/`, not `src/shared/`.** The `manualChunks` config in `vite.config.ts` merges `src/shared/**` (except `config/`) into a single eager chunk; placing locale files there would bundle every language and namespace into the initial load, defeating lazy loading.

These are maintenance conventions, not fully enforced import laws. The current ESLint architecture rule explicitly blocks deprecated root aliases such as `@/components/*`, `@/composables/*`, `@/utils/*`, `@/stores/*`, `@/types/*`, and `@/constants/*`; it does not automatically reject every cross-feature import. `src/features/agent` has its own plugin boundary rules, described below.

## State Boundaries

- Keep transient UI state in the component.
- Put page/module shared state in the owning feature's composable and use a store when warranted.
- Authentication is a global cross-cutting capability. Its current store is `src/shared/auth/authStore.ts`, not `features/auth/stores`.
- Keep server data in API/composable state unless it genuinely needs cross-page caching.
- Result-page typed arrays and reader instances are owned by composables/services and released when the run changes or the component unmounts.

## Background Work and Large Data

- Upload ZIP/MD5 work runs in `src/workers/zip-compress.worker.ts`.
- Annotation (database CSV parsing, feature matching, scoring, FDR and spatial-score computation) and KMeans run in workers owned by `vizworkbench` (`utils/annotation/annotation.worker.ts`, `kmeans.worker.ts`); the ion images used for annotation are read from Zarr on the main thread and handed to the worker.
- Zarr reads metadata and chunks as whole objects through the OSS client (`client.get(key)`, with no Range requests); the OSS client refreshes expired access credentials.
- UMAP is generated by the backend. KMeans is a local calculation over the UMAP embedding. Do not describe them as one backend job.

## SXO-Harness Plugin Structure

`src/features/agent` is a browser-side plugin application assembled by `@deepseek-ai/cordis`. See [Agent Architecture](./agent-architecture) for execution flow, event contracts, and recovery semantics.

- `bundles/base.ts` is the production composition; plugins declare service dependencies through `inject`. `bootstrap.ts` exposes `whenAgentReady()` to await every plugin.
- `bridge/` is the lightweight static page boundary for dataset identity, loading generation, and analysis selection. It must not import Cordis or plugins.
- `plugins/agent` provides the UI-facing `ctx.agent` facade for admission, session transitions, and snapshots. `plugins/agent-loop` registers the driver for turns, steps, attempts, and tool dispatch. Compaction, retries, binding, and result archives attach through events.
- `plugins/session` persists event batches before publishing facts. `session-projection` manages consistent read models; `session-transcript`, `token-meter`, and `agent-instructions` own transcript, statistics, and instruction projections. Streaming is an overlay; failed attempt output never enters model message history.
- `session-persistence` is the contract, and OPFS is its production implementation. Dataset-scoped conversations support recovery, cross-tab read-only access, temporary fallback, and ZIP migration with images. The log, model-visible surface, and UI message array represent different views.
- `connection` resolves address/key pairs, `llm` defines protocol-independent contracts, `llm-anthropic` isolates SDK dependencies, and `model-catalog` probes actual vision support. Registries supply domain tools and bundled skills.
- `FloatingAgent.vue` loads the workspace asynchronously and prefetches it during idle time. Closing the panel retains the module-level runtime; stopping a turn requires an explicit action.

ESLint restricts inter-plugin imports to `index.ts`, prohibits plugin-to-UI imports, isolates AI SDK use to `llm-anthropic`, and keeps the bridge runtime-free. Assign new capabilities to the facade, driver, policy, or read-model boundary before implementation.

## Automated Checks

- `npm run type-check`: Vue/TypeScript type checking.
- `npm run lint:check`: ESLint, the deprecated-root-alias restriction above, and the SXO-Harness plugin boundaries.
- `npm run test:unit:run`: one-shot unit test run.
- `npm run check`: runs those three commands in parallel.
- `npm run format:check`: checks Prettier for `src/` only and is not part of `check`.
- `npm run test:e2e:offline`: fixed-response regression in Chromium and Firefox without an account; see [Testing and E2E](./testing) for live integration boundaries.
- `npm run docs:type-check` / `npm run docs:build`: separately validate documentation types, production output, and most internal links.

When adding code, follow the responsibilities of the current neighboring implementation. If documentation and code disagree, confirm runtime behavior and update both.
